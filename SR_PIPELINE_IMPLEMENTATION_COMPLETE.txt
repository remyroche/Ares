================================================================================
CORRECT PIPELINE ORDER
================================================================================

STEP 1: sr_parameter_optimization
  ├─ Can run WITHOUT prior artifacts (first run)
  ├─ Uses clustering results from previous iteration if available
  ├─ Finds optimal parameters via Bayesian optimization
  └─ Produces: sr_parameter_optimization_result
               └─ optimized_parameters: {min_touches, strength_threshold, ...}

STEP 2: sr_detection
  ├─ Loads optimized_parameters from Step 1
  ├─ Applies those parameters to detect SR levels
  ├─ Falls back to defaults if optimization not available
  └─ Produces: sr_detection_result
               └─ levels: [detected SR levels]

STEP 3: sr_clustering
  ├─ Loads SR levels from Step 2
  ├─ Clusters the properly detected levels
  └─ Produces: sr_clustering_result, sr_levels_dictionary

       SRDetectionComponent,
       SRClusteringComponent

   param_result = await SRParameterOptimizationStep().execute(config)
   
   # Step 2: Detect (uses optimized parameters)
   det_result = await SRDetectionComponent().execute({
       **config,
       'use_optimized_parameters': True
   })
   
   # Step 3: Cluster
   clus_result = await SRClusteringComponent().execute(config)

COMPARISON: OLD vs NEW
================================================================================

❌ OLD (INCORRECT) ORDER:
1. sr_detection (default params)      → Suboptimal detections
2. sr_clustering (on bad detections)  → Poor clusters
3. sr_parameter_optimization          → Finds good params TOO LATE!

Problem: Optimized parameters never used! Wasted computation!

✅ NEW (CORRECT) ORDER:
1. sr_parameter_optimization           → Finds optimal parameters
2. sr_detection (uses those params)    → High-quality detections
3. sr_clustering (on good detections)  → Meaningful clusters

Benefits: Every step uses optimized outputs from previous steps!
