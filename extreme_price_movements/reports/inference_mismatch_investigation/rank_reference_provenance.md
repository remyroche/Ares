# Rank-Reference Provenance

Status: updated 2026-06-02.

## Question

Prove whether the policy rank-reference parquet is stale, copied from
`20260523_015947`, or generated from a different OOS prediction handoff than the
`meta_oof` files currently present under `20260525_010004_nopenalty`.

## Conclusion

The current `20260525_010004_nopenalty` rank-reference parquet is not a stale
copy from `20260523_015947` and is not generated from `meta_oof`. It is also
not generated from the deployed final-fit inference bundle.

It is generated by `simple_policy_optimiser` directly from
`policy_oos_predictions/*_clf.parquet`. Those policy-OOS files were generated
by `scripts/generate_policy_oos_predictions.py` from the frozen
`models/model_state_meta.pkl` train-meta state, with manifest fields:

- `model_provenance = train_meta_frozen_model_state`
- `prediction_source = generated_from_train_meta_state:labels`
- `generated_from_final_fit_bundle = false`
- `source_model_state_sha256 = 3b19d54aca1298e10d177c90560839bd804e960df602ca97020d1893f55204c8`
- `source_model_fit_end = 2024-09-08T04:00:00+00:00`
- `policy_predict_start = 2026-01-22T10:00:00+00:00`

This localizes the remaining policy-score mismatch: saved policy reference
scores are frozen policy-OOS train-meta-state scores, while the mismatching
historical replay scores were final-fit inference replay scores. The
rank-reference itself is not stale.

### Exact rank-reference source reproduction

Joining active per-strategy rank-reference files to their matching
`policy_oos_predictions/policy_oos_*_clf.parquet` files on
`timestamp`, `symbol`, and `strategy_id` showed exact row/key overlap for each
strategy checked.

For every strategy checked:

- `rank_reference.calibrated_score == policy_oos.clf` exactly.
- Applying `calibrated_score_and_threshold(...)` to `policy_oos.clf` also
  reproduced `rank_reference.calibrated_score` exactly.
- Maximum absolute difference was `0.0`; non-zero differences above `1e-12`
  were `0`.

The current rank-reference score transform is therefore an identity transform
for these policy-OOS files; the rank CDF is calculated from the saved policy
OOS `clf` score distribution.

## Confirmed Bug

The saved policy metrics metadata was misleading. It used the request flag
`EPM_SIMPLE_POLICY_USE_PRECOMPUTED_META_OOF` as if it were the actual source.
When precomputed OOF was requested but unavailable for the policy slice, the
optimizer correctly fell back to final-fit model generation, but
`prediction_source.source` could still say `precomputed meta_oof parquet
OOS/OOF predictions`.

Patch:

- `simple_policy_optimiser.py` now records requested versus actual prediction
  source separately.
- Top-level metrics include actual source strings and labels per strategy.
- Per-strategy metrics use the actual source when setting
  `uses_precomputed_meta_oof`.

This patch changes only reporting/provenance metadata; it does not change
trading rules, scores, ranks, thresholds, model inputs, or artifacts.

## Investigation Implication

The remaining systemic mismatch is not that the rank-reference is stale. It is
that policy-OOS scores are generated from a held-out frozen train-meta state,
while final-fit inference replay scores are generated from the deployed
final-fit inference bundle. A final-fit bundle may be correct for live trading,
but it is not itself a valid OOS scorer for policy optimisation unless its fit
window is proven to exclude the policy-OOS rows.

The next parity question is therefore not "which file is stale"; it is whether
the policy-OOS scorer, deployed scorer, feature contract, rank-normalization,
source-parity filters, and deployment-mask contracts are explicitly versioned and
guarded so the optimizer cannot mix held-out policy evidence with a different
deployed scorer or gating contract. The latest regenerated run now has seven
policy-OOS/rank-reference inputs and a four-strategy deployed portfolio selected
from them.
